# Arkana Civiel Legal Management — V5.1 QA

Date: 2026-09-26
Branch: `v5-wordpress-foundation`

## Scope

Static/code review of V5.1 data model, WordPress registration, role/capability handling, relationship persistence, input validation, and production-readiness boundaries.

## Result

**FOUNDATION: PASS**

**PRODUCTION: NOT READY**

V5.1 establishes the intended data relationships, but several hardening items must be completed before real client/case data is permitted.

## Verified

- 7 WordPress custom post types are registered: Client, Matter, Legal Request, Task, Deadline, Document, Retainer.
- Core relationships are represented through post meta.
- Matter supports Client, Partner, and Lead Lawyer relationships.
- Request supports Client and Matter relationships.
- Task supports Client, Matter, and Assignee relationships.
- Deadline supports Matter relationship.
- Document supports Client, Matter, document type, and access level.
- Retainer supports Client relationship and dates.
- Relation editor uses a WordPress nonce.
- Save handler rejects autosaves/revisions and checks `edit_post` capability.
- Select values are allow-listed before persistence.
- User and post relationship IDs are normalized with `absint`.

## Findings to fix before V5.2/production

### V51-01 — Relationship consistency validation
**Severity: High**

A Task, Request, or Document can currently store a Client ID that does not match the Client belonging to its selected Matter. The UI allows independent selection. A server-side invariant is required:

`matter.client_id == child.client_id` whenever both are present.

The same principle should be applied to Request, Task, and Document.

### V51-02 — Matter/child referential integrity
**Severity: High**

The save handler validates that a referenced post ID is numeric, but it does not verify the referenced post exists and has the expected post type. Server-side validation must reject invalid/stale relationships.

### V51-03 — WordPress capability completeness
**Severity: High**

The custom roles currently receive only a subset of the capabilities generated by `map_meta_cap` for array-based `capability_type`. A complete capability matrix is required for create/edit/delete/publish/private content operations. V5.2 will replace the broad internal capability assignment with explicit role-by-module permissions.

### V51-04 — Client roles must remain isolated
**Severity: Critical for production

Client Admin and Client User must not receive generic access to internal CPTs. Matter-level authorization must be enforced in every dashboard, REST, document, and query path. This is a V5.5/V5.9 prerequisite.

### V51-05 — REST authorization
**Severity: Critical for production

`show_in_rest` is enabled to support the future portal, but endpoint-level authorization must be added before sensitive objects are exposed through REST. Do not expose production client data through the default WordPress REST API until permissions are enforced.

### V51-06 — Private document handling
**Severity: Critical for production

The Document CPT currently models metadata only. It is not yet a secure private-file delivery system. Real legal documents must wait until V5.9 private document storage/delivery and access logging are implemented.

## V5.1 acceptance criteria

V5.1 can be considered complete when:

- [ ] Relationship IDs are type-checked server-side.
- [ ] Client/Matter consistency is enforced server-side.
- [ ] Role capabilities are explicitly mapped.
- [ ] Client roles cannot access internal records outside their authorized matters.
- [ ] REST access is permission-gated.
- [ ] Automated regression tests cover relationship invariants.
- [ ] No production client data is used in Local/QA.

## Decision

Keep V5.1 as the **data-model foundation**, but carry the security/authorization hardening into V5.2 and V5.9. Do not migrate V4 production data or deploy the plugin to the live Arkana Civiel website yet.
